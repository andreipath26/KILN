# KILN Pipeline Design

Status: DRAFT
Owner: project lead
Created: 2026-10-03
Purpose: Design document for the end-to-end inference pipeline. Anchors
the minimal working path that connects all crates.

## Non-goals

This document does not specify real GGUF loading. It does not specify the
chat loop. It does not specify tokenization. It specifies the minimal
pipeline that loads a synthetic model, produces one output, and exits.
Real model support is Phase 1 late or Phase 2.

## Why this exists

Eight crates exist. They compile. They have tests. But no program has ever
run through all of them in one process. The pipeline is the piece that
proves the plumbing works. Until a single program loads a model, selects a
plan, executes it, and produces output, the runtime does not exist.

## The minimal end-to-end path

The pipeline runs five steps in order.

Step 1. Load. Read a synthetic model from a file. The file contains a
weight matrix, an activation vector, a scale, and a manifest.

Step 2. Select. Call the Mode Selector with the manifest and the current
performance envelope. Get an ExecutionPlan.

Step 3. Schedule. Create a Scheduler with the plan. Step through the plan
node by node.

Step 4. Execute. For each node, dispatch to the appropriate kernel. The
only kernel needed for the first version is the scalar fused ternary
matmul.

Step 5. Output. Print the result and the timing breakdown.

## What load a model means for the first version

Real GGUF files are complex. They have metadata, tensor tables, alignment
rules, and multiple quantizations. Loading a real GGUF is a Phase 1 late
task.

For the first pipeline, load a model means reading a synthetic file with
a simple format.

The header is text, one field per line.

KILN_SYNTHETIC_v1
num_rows: N
num_cols: M
scale: F
weights: <N times M trits packed in TQ1.0>
activations: <M int8 values>

The header is text. The weights and activations are binary. The loader
reads the text header, then reads the binary sections.

The synthetic model is generated by a separate tool, kiln-synth, which
lives in kiln-bench. It takes N, M, and a seed and produces a valid
synthetic file.

## The pipeline crate

The pipeline lives in kiln-core, in a new module called pipeline.rs. It
does not add a new crate. It uses the existing crates.

The pipeline exposes one function.

pub fn run_once(path: PathBuf) -> Result<PipelineReport, PipelineError>;

It reads the synthetic model at path, runs the five steps, and returns a
report with the output and the timing.

The PipelineReport has these fields.

output is f32.
load_time_nanos is u64.
select_time_nanos is u64.
schedule_time_nanos is u64.
execute_time_nanos is u64.
total_time_nanos is u64.
nodes_executed is u32.

## What the pipeline exercises

Every crate in the runtime is touched.

kiln-models reads the manifest and the quantization spec.
kiln-hal registers a CPU backend with the Registry.
kiln-mem reports the tier state.
kiln-io reads the synthetic file from disk.
kiln-kernels invokes the scalar fused matmul.
kiln-core runs the selector and the scheduler.
kiln-cli exposes the kiln pipeline command.

kiln-api is not touched. It is the REST server. It comes later.

## The CLI command

The pipeline is invoked from the CLI.

kiln pipeline path

It reads the synthetic file, runs the pipeline, and prints the report.
The human-readable output shows the five times and the output value. The
json flag prints the report as JSON.

## Timing breakdown

The timing is the point of this exercise. It tells us where the time goes
on the Dell 7490. Four numbers matter.

load_time_nanos is mostly file I/O and pack and unpack.
select_time_nanos is the selector five-step algorithm.
schedule_time_nanos is walking the DAG.
execute_time_nanos is the kernel invocation.

For a small synthetic model, the execute time should dominate. If load or
select dominates, there is a bug in the pipeline that we need to find.

The expected breakdown for a 1024-element row.

load approximately 10000 ns.
select approximately 5000 ns.
schedule approximately 1000 ns.
execute approximately 3000 ns.
total approximately 19000 ns.

These are estimates. The actual numbers are the deliverable.

## Error handling

The pipeline returns a PipelineError for file not found, malformed
header, weight data truncated, selector returned an empty plan, scheduler
reported an error, or kernel returned non-zero.

Each error names the exact step and the exact reason. Rule KILN-E4 applied
to the pipeline boundary. When the pipeline fails, the error says exactly
where.

## Testing strategy

Three tests.

One. Unit test. Generate a small synthetic file in a temp directory, run
the pipeline, verify the output matches a hand-computed value.

Two. Integration test. Generate a 1024-element synthetic file, run the
pipeline, verify all five timing fields are non-zero and the output is
finite.

Three. Property test. Generate 100 random synthetic files with different
seeds, run the pipeline on each, verify none panic and all produce finite
output.

## What comes after the pipeline

Once the pipeline runs end to end on a synthetic model, the next steps are
real GGUF loading, real tokenization, the chat loop, streaming output, and
the scheduler thermal response.

Each of those is a separate design document and a separate commit.

## Open questions

The synthetic file format is text-header plus binary. Is this sufficient,
or should it use a real container format from the start.

The pipeline runs one matmul. A real model runs hundreds. Should the
pipeline run multiple layers from the start.

The pipeline invokes the kernel directly. Should it go through the
Registry dispatch. The Registry is the correct path for production.

How does the pipeline report a thermal event during execution. The
scheduler knows. The pipeline needs to know too.
